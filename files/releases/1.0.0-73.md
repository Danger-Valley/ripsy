# RIPSY 1.0.0 (73)

Release date: 2026-11-02. Product source `2780fa3`, plus synchronized native
build counters 73; marketing version 1.0.0. User requested TestFlight, Android
with standing Download publication, and the backend. Existing bare React Native
Community CLI projects and locked dependencies are retained; no Expo.

## Scope and checks

Packages the startup/foreground server-figure resource synchronization from
`5904f25`: cached manifest restoration, bounded public manifest retries, two
background prefetch workers, exact-byte/SHA checking, optional independently
versioned private PNG caching, LRU/budget limits and preserved controllers.
Build 72 already loaded unknown fighters on demand; this release adds the
startup/private-PNG enhancement. The backend/admin upload workflow is independent
of native rendering and does not add any new fighter or pack reward by itself.

Fresh 818 mobile tests/59 suites with open-handle detection, mobile TypeScript,
eight-model PNG/Rive digest/geometry/timeline/input checks and both-platform
release preflight pass. Live health/Redis/configured push, original prices,
paused buyer-prepaid backend packs and public native Privy configuration pass.
Sixteen live PNG/Rive resources match the manifest byte lengths and hashes.
Configured push is not a delivery test; no real wallet/payment, on-chain
transaction, physical-device download/offline or purchase test was performed.
Existing dependency advisories remain open; this is not a security-audit closure.

Build processes inherit an allowlist of standard runtime variables and public
native Privy identifiers, never private root `.env` backend values. A bounded
27-pattern local-private-value representation scan finds zero matches in APK,
archive app and exact distribution IPA, with all five canonical bundled Rives
present. This is not a comparison against every Railway variable or every secret
that may ever have existed. No key/authority/treasury/collection, pack policy,
update-minimum or authentication behavior was changed for this release.

## Storage decision and retained limitations

Read-only Railway API confirms the existing Redis volume
`c0b05bf6-3e21-47e9-8fcf-ae06dd35f694`, instance
`4946b59d-cb08-41a4-ae06-31797c73d152`, /data, 5000MB provisioned and about184.55MB
currently used. Backup list and backup-schedule list are empty. The user
explicitly declined enabling Railway backups because a platform migration is
planned; no backup, schedule, restore or Redis setting was changed.

Current runtime persistence is Redis, including games, wallet bindings, loadouts,
orders and shop settings. Firebase is FCM, not a configured Firestore database;
MongoDB/Supabase are not connected in this codebase. Existing eight figure files
stay on their original public hosting, not moved into Redis. Only the new admin
upload path writes new file bytes/metadata and registrations to Redis. The
operator did not upload/publish any additional fighter. A persistent catalog/order
database plus separate object storage is the intended architecture discussion
for the coming migration; destination and implementation are not approved here.
Do not treat the current bounded Redis upload implementation as a completed
long-term asset-storage/recovery solution or infer authorization to provision a
new database, migrate/delete data or change the live upload workflow.
